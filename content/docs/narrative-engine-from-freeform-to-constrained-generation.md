用大模型做过叙事的人大概都遇到过这种情况：你定义了一个角色，前两轮对话表现很好，第三轮开始做出不符合人设的事，第五轮开始胡乱添加阴谋，第十轮已经完全忘记了最初的世界观。

这不是模型不够好，而是“自由生成”的本质缺陷——大模型没有“必须遵守规则”的内置机制。想让 AI 稳定叙事，需要一种方式把规则写下来，让模型必须遵循。

> 于是我写了 Mephisto——一个用 Go 实现的长线叙事引擎。它的核心工作方式是：创作者用纯文本契约文件（`.meph`）定义角色、世界观和规则，引擎读取后通过规则匹配和 LLM 调用生成叙事。但本文不讨论引擎的运行机制，而是从最基础的问题开始：这份契约文件应该用什么格式？

它需要承载的内容包括角色信息、世界观设定、状态变量和行为规则——有单行文本、多行文本、键值对列表，也有条件-动作组合。而这个引擎需要的第一样东西，是一种能把规则写清楚的格式。

格式的选择，决定了创作者是在"写故事"还是在"Debug 语法"。

### 一、JSON

JSON 是最自然的选择。它结构清晰、解析简单、几乎所有编程语言都有现成的库。一个角色定义用 JSON 写出来大致是这样：

```json
{
  "role_name": "贝利亚奥特曼",
  "anchor": [
    { "key": "核心信念", "value": "力量就是一切" },
    { "key": "说话风格", "value": "狂傲、嘲讽" }
  ],
  "worldview": "光之国是宇宙中最强大的文明……",
  "background": "曾是光之国的战士，后来堕入黑暗……",
  "state": {
    "堕落指数": 85,
    "情绪": "暴怒"
  },
  "rules": [
    {
      "name": "攻击",
      "condition": "包含 \"攻击\"",
      "action": "注入 \"贝利亚发动了猛烈的攻击\""
    }
  ]
}
```

技术上看，这没有任何问题。程序可以正常读取、解析、执行。

但问题在于，这个文件的作者是创作者，而不是程序员。一个想定义角色的故事作者需要面对：

- 花括号的配对
- 引号嵌套（规则条件里的引号还要转义）
- 逗号不能多也不能少
- 数组和对象的区分

这些对于开发者来说是常识，但对非技术用户来说，每一个都是潜在的错误点。

尤其值得注意的是 **JSON 中的字符串转义**。创作者的意图是写一句规则条件：

```
包含 "攻击"
```

但在 JSON 里必须写成：

```json
"condition": "包含 \"攻击\""
```

这意味着创作者在书写时不能直接表达自己的意图，必须时刻思考“我是在写 JSON 还是在写规则”——这种心智切换，在大型契约中会累积成巨大的认知负担。

哪怕只是漏掉一个逗号，整个文件就无法解析。JSON 解析器的报错信息对非技术用户来说也几乎不可理解。

**小结：JSON 对程序友好，但对创作者不友好。**

### 二、YAML

YAML 比 JSON 更适合非技术用户。它不需要花括号和逗号，用缩进表示层级，可读性明显更好：

```yaml
role_name: 贝利亚奥特曼
anchor:
  - 核心信念: 力量就是一切
  - 说话风格: 狂傲、嘲讽
worldview: |
  光之国是宇宙中最强大的文明……
state:
  堕落指数: 85
  情绪: 暴怒
rules:
  - name: 攻击
    condition: 包含 "攻击"
    action: 注入 "贝利亚发动了猛烈的攻击"
```

看起来不错。但 YAML 有它自己的问题。

首先是**缩进的敏感性**。YAML 完全依赖缩进来表达层级，意味着用户必须精确控制空格的数量。一个多余的空格或一个缺失的缩进，就会导致解析失败或产生意想不到的结构。这类错误非常难以排查。

尤其值得注意的是：在 YAML 中，一个三级嵌套的规则配置需要精确控制三个层级的缩进，每缩进一次，视觉上就增加一分混淆的可能。对于动辄上百行的契约文件，这种认知负担是持续累积的——你不是在阅读内容，而是在不断核对“这一行到底缩进了几个空格”。

其次是**格式的复杂性**。YAML 看起来很“简单”，但实际上语法规则相当多——`|` 表示保留换行、`>` 表示折叠换行、`&` 和 `*` 表示锚点和引用……这些功能虽然强大，但大多数用户根本用不到，反而增加了学习成本。

第三是**多行文本与列表的意外交互**。当一个 YAML 文件中既有 `|` 定义的多行文本块，又有普通的键值对和列表时，缩进层次稍有偏差，解析器就可能把多行文本误认为列表项的子元素，或者反过来。这种“非预期行为”通常不会产生语法错误，而是产生逻辑错误——文件能读，但行为完全不对。

**小结：YAML 比 JSON 更接近人类，但它的“简单”是一个错觉。**

### 三、纯文本（TXT / Markdown）

既然 JSON 太“程序员”、YAML 有陷阱，那能不能干脆不用结构化格式，直接用纯文本？

比如用户直接写：

```
角色名：贝利亚奥特曼
核心信念：力量就是一切
世界观：光之国是宇宙中最强大的文明……
规则1：当用户提到攻击时，注入攻击描述
```

这种写法人人都会，上手难度为零。但问题随之而来：

- 如何区分“角色名”和“世界观”和“规则”？
- 规则的条件和动作如何解析？
- 多行文本和单行键值对如何共存？

纯文本的自然语言虽然对人类友好，但对程序来说太过模糊。如果我用纯文本，就需要花大量精力去设计一套“隐式规则”——比如通过关键词匹配来识别区块类型，通过换行来区分条目。这比显式的语法更难保证正确性。

Markdown 稍微好一点，可以用 `#` 表示标题、`-` 表示列表，但它的设计目标是“排版”，而不是“数据结构”。用 Markdown 来承载业务数据，本质上是在用排版语法模拟结构化存储——能做，但别扭。

**小结：纯文本对创作者最友好，但对程序几乎不友好。**

### 四、格式对比总结

| 格式   | 对创作者友好 | 对程序友好 | 主要问题                         |
| ------ | :----------: | :--------: | -------------------------------- |
| JSON   |      ❌      |     ✅     | 语法符号过多，非技术用户难以掌握 |
| YAML   |      ⚠️      |     ✅     | 缩进敏感，多层嵌套认知负担高     |
| 纯文本 |      ✅      |     ❌     | 结构模糊，程序无法精确解析       |

我需要一种格式，它同时满足两个条件：

1. **对创作者友好**——写起来像在写文档，而不是在写代码
2. **对程序友好**——有明确的规则，可以被精确解析

这意味着我需要设计一种专门的格式。

### 五、.meph 的设计

于是我定义了一种格式，后来命名为 `.meph`。它的核心设计原则只有三条：

**1. 用人类语言做区块边界，消除括号恐惧**

创作者看到的不是 `{` 和 `}`，而是 `【角色名】` 和 `【规则】`。中文书名号对中文创作者来说比花括号更自然，而且“角色名”三个字本身就说明了这块内容是什么，不需要额外的注释。

**2. 区分“语义区块”，而非“数据结构”**

在 JSON 中，创作者需要自己决定用对象还是数组——这属于实现细节。在 `.meph` 中，创作者只需要知道“这是一个列表”或“这是一段话”。“角色名是单行文本”、“规则是列表”这些信息由解析器来识别，不由创作者来声明。

**3. 语法贴近自然逻辑**

规则采用 `[规则名] if 条件 -> 动作` 的直觉表达式，条件中的逻辑运算符用 `包含`、`状态.键 > 值` 这类可读性强的写法，而不是纯符号。

最终，一个完整的 `.meph` 文件长这样：

```meph
【角色名】
贝利亚奥特曼

【锚点】
- 核心信念：力量就是一切
- 说话风格：狂傲、嘲讽

【世界观】
光之国是宇宙中最强大的文明。
奥特之王在三千年前就已经预见了这场战争。
（区块内支持自然换行，直到遇到下一个【】区块标记）

【状态】
- 堕落指数：85
- 情绪：暴怒

【规则】
[攻击] if 包含 "攻击" -> 注入 "贝利亚发动了猛烈的攻击"
[光之国] if 包含 "光之国" -> 注入 "{角色名}的故乡是光之国"
```

> **关于 `{角色名}`：** 这是插值语法，用于在文本中引用状态变量。它的具体实现会在系列后续文章中详细展开。

### 六、这种设计的代价

这种设计不是没有代价的。

- **解析器更复杂**：我不能直接用 `json.Unmarshal` 或 `yaml.Unmarshal`，需要自己写 Lexer 和 Parser
- **格式需要文档**：创作者需要学习这个格式的写法，虽然学习成本比 JSON 低，但毕竟需要学习
- **工具链缺失**：没有现成的语法高亮、格式化、校验工具

但这里有一个关键区别：创作者学习的内容不是“语法符号”，而是“区块类型”。用户只需要知道“有哪几种区块”以及“每种区块里写什么”，而不是“如何用符号表达嵌套关系”。前者是概念性的，后者是符号性的——概念性的学习是“知道有这个东西”，符号性的学习是“时刻记住该怎么写”。

但换来的是对创作者真正的友好，以及在错误提示上的巨大优势。

JSON 的报错是这样的：

```
Unexpected token } in JSON at position 246
```

一个非技术用户看到这个信息，只能复制粘贴去搜索引擎碰运气。

而 `.meph` 解析器可以这样报错：

```
[第 12 行] “状态”区块下的条目必须以“-”开头，但这一行没有找到
```

创作者可以精确地定位到具体行号，并理解问题所在——不需要理解“token”是什么，也不需要知道“position 246”对应文件的哪个位置。

这个取舍，我后来认为是值得的。
