## 引言：解析完成了，然后呢？

前三篇完成了解析层的工作：契约被加载，规则被解析，插值语法被识别。解析器输出 `domain.Contract`，里面包含了角色名、状态初始值、规则列表等结构化数据。

但解析器的工作到此为止。`Contract` 只是一堆静态数据——角色名是字符串，规则是条件-动作表达式，状态是键值对。它自己不会说话，不会决策，不会叙事。

**谁来驱动它？**

答案是引擎。引擎拿到 `Contract` 后，进入一个循环：接收用户输入 → 匹配规则 → 执行动作 → 调用 LLM → 返回响应。每一轮对话都在这个循环中运转。

不过，规则匹配和动作执行的具体实现——条件表达式怎么评估、动作类型怎么分发、LLM 客户端怎么调用——这些是标准操作。市面上已经有大量关于 LLM 集成的文章，这里不再重复。

本篇要做的是另一件事：**当对话超过 100 轮之后，引擎怎么让 LLM 还记得最初的角色设定和发生过的事情？**

这是长线叙事引擎区别于普通聊天机器人的关键。


## 一、问题：LLM 没有长期记忆

LLM 的上下文窗口有限。DeepSeek 当前的上下文窗口约为 64K tokens，听起来很大，但在一场长篇叙事中，十几轮对话就可能耗尽。更关键的是，**上下文窗口不是存储，而是缓存**——它只保留当前会话中的内容，一旦超出，最早的消息就被丢弃。

这意味着什么？

意味着如果没有任何额外机制，一个角色在故事开头的经历，在 50 轮对话之后就会被遗忘。它不会记得自己见过谁、做过什么、承诺过什么。叙事失去了连续性。

**记忆系统的职责就是解决这个问题：把对话历史中的关键事件提取出来，以压缩的形式长期保存，并在每一轮对话中注入回 LLM 的上下文。**


## 二、引擎的完整闭环

在深入记忆系统之前，先看一下引擎的完整闭环：

```
┌─────────────────────────────────────────────────────────────┐
│                        每一轮对话                          │
│                                                             │
│  用户输入 ──→ 规则匹配 ──→ 动作执行 ──→ LLM 生成 ──→ 响应  │
│                │            │           │                   │
│                │            │           │                   │
│                ▼            ▼           ▼                   │
│          [条件评估]   [状态/记忆修改]  [流式输出]           │
│                                                             │
│                      ▼ 对话结束后                          │
│                 记忆提取（每 N 轮触发）                     │
│                      │                                      │
│                      ▼                                      │
│                  保存到记忆库                               │
│                                                             │
│                      ▼ 下一轮开始前                        │
│                  记忆注入 LLM 上下文                        │
└─────────────────────────────────────────────────────────────┘
```

记忆系统嵌入在循环的尾部（提取）和头部（注入）。它不参与单轮对话的即时决策，但它决定了角色在长期叙事中能“记得”什么。


## 三、触发策略：每 N 轮提取一次

不是每一轮对话都需要提取记忆。大多数时候，对话只是普通的交流，不包含值得长期记录的事件。

所以记忆系统需要一个**触发策略**：每隔 N 轮提取一次。

```go
type MemoryConfig struct {
    ExtractInterval int  // 每 N 轮提取一次，默认 5
    MaxLimit        int  // 记忆条数上限，默认 30
    CompressRetain  int  // 压缩时保留的最新条数，默认 5
    ExtractWindow   int  // 提取时参考的最近对话轮数，默认 10
}
```

判断逻辑很简单：

```go
func (m *MemoryManager) ShouldExtract(round int) bool {
    return round > 0 && round % m.config.ExtractInterval == 0
}
```

当对话进行到第 5、10、15、20 轮时，触发提取。提取时只取最近 10 轮对话（`ExtractWindow = 10`），避免传入 LLM 的上下文过长。

**这个设计背后的思考是：** 大多数对话轮次不需要记忆，真正值得记住的关键事件——冲突、转折、重大决策——每隔几轮才会出现一次。与其每轮都调用 LLM 提取摘要（浪费 token 且可能产生噪音），不如按固定间隔批量处理。


## 四、提取：让 LLM 给自己做摘要

记忆提取的核心是：**让 LLM 从对话历史中提炼关键事件摘要**。

提示词模板如下：

```
从以下对话中提取关键事件摘要。

规则：
1. 每条摘要不超过 20 个字
2. 只提取对角色产生重大影响的事件
3. 忽略日常寒暄和无意义对话
4. 如果事件已经存在于现有记忆中，不要重复提取
5. 输出格式：每行一条，以 "- " 开头

现有记忆：
{existing_memories}

对话历史：
{history}

请输出新提取的记忆：
```

举个例子。假设历史记录包含这样一段：

```
命运: 你来到了光之国
角色: 贝利亚悬浮在光之国上空，俯视着下方戒备的战士们
命运: 奥特之父挡在了你面前
角色: 贝利亚发出一声冷笑
```

LLM 可能提取出：

```
- 贝利亚抵达光之国，遭遇奥特之父
```

20 个字以内，抓住了关键事件，丢弃了细节。

**这个设计的精妙之处在于：** 提取和叙事用的是同一个 LLM。引擎不需要额外的 NLP 模型来做摘要，只需要设计好提示词，让 LLM 读自己的输出、写自己的摘要。这有点像人类回顾自己的经历并写日记——不是逐字记录，而是压缩、重构、保留意义。

### 防御性解析：不信任 LLM 的格式

在实际工程落地中，大模型偶尔会产生“格式幻觉”——在返回的记忆列表前后加上寒暄语（如“好的，以下是新提取的记忆：”），或者使用 `*` 而不是 `-`，甚至混入空行和多余的空格。

因此，引擎在拿到 LLM 的提取结果后，会进行一层防御性清洗：

```go
func parseMemoryLines(text string) []string {
    var result []string
    for line := range strings.Lines(text) {
        line = strings.TrimSpace(line)
        if line == "" {
            continue
        }
        // 去掉 "- " 或 "* " 前缀
        line = strings.TrimPrefix(line, "- ")
        line = strings.TrimPrefix(line, "* ")
        line = strings.TrimSpace(line)
        if line != "" {
            result = append(result, line)
        }
    }
    return result
}
```

这个函数做了三件事：
1. **逐行扫描**，避免整段被污染
2. **兼容 `-` 和 `*`**，包容 LLM 的格式变化
3. **丢弃空行和无效行**，只保留有效内容

这样即使 LLM 在输出中加了“好的，以下是结果：”，解析器也能精准地提取出真正的记忆条目。**永远不要信任 LLM 的输出格式——信任需要代码来保障。**


## 五、去重与压缩

### 去重：纯粹的工程取舍

新提取的记忆可能与现有记忆内容重复。在去重策略上，我没有选择向量数据库或 Embedding 语义相似度计算，而是采用了最朴素的**字符串集合精确匹配**：

```go
func filterDuplicateMemories(newMemories, existing []string) []string {
    existingSet := make(map[string]bool)
    for _, mem := range existing {
        existingSet[strings.TrimSpace(mem)] = true
    }

    var result []string
    for _, mem := range newMemories {
        if !existingSet[strings.TrimSpace(mem)] {
            result = append(result, mem)
        }
    }
    return result
}
```

**为什么不用语义相似度？**

1. **零依赖：** 避免为了一个去重功能引入向量模型、Embedding API 和额外的工具链，保持引擎的轻量
2. **包容细节重叠：** “贝利亚抵达光之国”与“贝利亚抵达光之国，遭遇奥特之父”在语义向量上可能接近，但后者是全新的剧情推进。语义去重极易误杀关键信息
3. **边际收益递减：** 配合简单的文本清洗（去除首尾空格、统一标点符号），精确匹配已经能过滤掉 90% 以上由 LLM 自身复述产生的完全重复项。剩余的微小表达差异（如多一个“了”字），留在记忆库里反而能丰富 LLM 的认知

这是一个典型的 **80/20 取舍**：用 20% 的工程投入（几行字符串匹配）解决了 80% 的问题，避免了用 80% 的投入（向量数据库 + Embedding 流水线）去解决剩余 20% 的边际问题。

### 压缩：当记忆超过容量时

当记忆条数超过上限（默认 30 条）时，触发压缩。

压缩策略是：将前 25 条压缩为 3-5 条摘要，保留最近 5 条不变。

```
压缩前：[M1, M2, M3, ..., M25, M26, M27, M28, M29, M30]
          ↓ 压缩
压缩后：[Summary1, Summary2, Summary3, Summary4, M26, M27, M28, M29, M30]
```

压缩同样由 LLM 完成。提示词模板：

```
以下是一段角色的长期记忆列表。请将这些记忆压缩为不超过 5 条最重要的摘要。

要求：
1. 保留最关键的 3-5 个核心事件
2. 保留最近发生的重要事件
3. 合并相似或重复的记忆
4. 每条摘要不超过 20 个字
5. 输出格式：每行一条，以 "- " 开头

现有记忆：
{memories}

请输出压缩后的记忆：
```

这个设计的权衡是：**压缩会丢失细节，但保留了关键事件的骨架。** 对于长篇叙事来说，骨架比细节更重要——角色不需要记得每一场战斗的每个动作，但需要记得自己为什么而战、敌人是谁、盟友在何方。


## 六、记忆的生命周期

把以上所有部分串起来，记忆的完整生命周期是：

**1. 加载时**

契约中的 `【记忆】` 区块被解析为初始记忆，作为角色的“背景记忆”注入引擎。

**2. 对话中**

每轮对话结束后，如果 `ShouldExtract` 返回 `true`，引擎调用 LLM 提取新记忆。

提取结果经过**防御性清洗**和**去重**后追加到记忆列表末尾。

**3. 检查上限**

如果记忆条数超过 `MaxLimit`（30 条），触发**压缩**。

压缩结果替换旧的记忆列表，保留最近 `CompressRetain`（5 条）不变。

> **4. 下一轮对话开始前**
>
> 所有记忆作为上下文注入 LLM Prompt：
>
> ```
> 【格式硬性要求】
> （NarrativeConstraints——禁止剧本格式、禁止括号动作描述、禁止独角戏）
>
> 【世界观】
> ...
>
> 【当前状态】
> ...
>
> 【你记得的过往】
> - 贝利亚抵达光之国，遭遇奥特之父
> - 贝利亚摧毁了一艘追击飞船
> - ...
>
> 【此刻】
> （用户输入）
> ```
> 注意 Prompt 的第一层不是世界观或角色名，而是一组硬性格式约束（`NarrativeConstraints`）。它的作用是告诉 LLM“什么绝对不能做”——禁止用括号描述动作、禁止用冒号加引号标注对话、禁止只有玩家独角戏。这组约束在每一轮对话中都存在，始终悬挂在 Prompt 的顶部和底部。它和第一篇讨论的“约束生成”理念是一脉相承的——不是在规则层用代码拦截，而是在 Prompt 层用“禁止”替代“建议”，直接掐断 LLM 输出剧本格式的可能性。

**5. 退出时**

记忆随子版存档一起保存到 `.meph` 文件的 `【记忆】` 区块中。下次加载时，从契约中恢复。


## 七、小结：解析器 + 规则引擎 + 记忆系统

四篇文章走完了一条完整的叙事线：

| 篇目 | 解决的问题 | 核心产出 |
|------|----------|----------|
| 第一篇 | 为什么不用 JSON/YAML？ | 格式设计的取舍 |
| 第二篇 | 怎么精确解析并报告错误？ | 手写 Lexer + Parser |
| 第三篇 | 规则和 {变量} 怎么解析？ | 规则表达式解析 + 插值语法 |
| **第四篇** | **100 轮后还记得你是谁？** | **记忆编织系统** |

解析器负责“读剧本”——把 `.meph` 变成 `Contract`。

规则引擎负责“做决策”——匹配条件、执行动作。

记忆系统负责“记住剧情”——提取关键事件、压缩、注入。

三者加起来，就是一个完整的长线叙事引擎。

```
契约（.meph）
    │
    ▼
解析器 ──→ Contract
    │
    ▼
规则引擎 ──→ 单轮决策
    │
    ▼
记忆系统 ──→ 长期连续性
    │
    ▼
LLM 叙事输出
```
